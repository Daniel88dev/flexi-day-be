# Microsoft Graph for own-calendar sync

Researched 2026-10-11 against Microsoft Learn (Graph v1.0 and beta reference, Microsoft Entra
identity platform docs), the npm registry and the `microsoftgraph/msgraph-sdk-javascript`
repository, all as published on that date. Every section lists the pages it rests on; the date after
a URL is that page's `ms.date`, the author's last substantive revision.

Scope: one-way sync of a user's own approved absences into their own Microsoft calendar, default
calendar by default, for work, school and personal accounts through the existing multitenant
registration (`common`). Absences show as Out of office; Home office days set a work location of
Home where an API allows it. The backend runs its own OAuth flow and holds the refresh token; there
is no MSAL.

## Answer

1. **Out of office works on v1.0 for both account classes.** `showAs` on `event` takes `oof`, both
   on an all-day event (start and end at midnight in the same time zone) and on a timed one. Create,
   update and delete of events, and create and list of calendars, each list `Calendars.ReadWrite`
   for delegated work or school accounts and for delegated personal Microsoft accounts alike. The
   known-issues page lists nothing for calendars beyond large attachments on shared mailboxes.
2. **Yes, there is an API that sets a user's work location, and it covers less than the spec
   wants.** `workHoursAndLocationsSetting` under `/me/settings/workHoursAndLocations` went GA on
   v1.0 in December 2025 under `Calendars.ReadWrite`. It is work or school accounts only: every
   method says "Not supported" for personal Microsoft accounts. Two limits matter. `setCurrentLocation`
   sets `office` or `remote` for the current day or current segment only. `POST .../occurrences`
   creates `timeOff` occurrences only; `remote` and `office` occurrences "are autogenerated from
   recurrences". So a future Home office day has no documented write. What the spec can do for a
   Microsoft work account: call `setCurrentLocation` with `remote` and `currentDay` on the morning of
   the day, or write nothing. For a personal account, write nothing. A `timeOff` occurrence is also a
   legitimate second representation of an absence, next to the `oof` event, for work accounts.
3. **`Calendars.ReadWrite` is the only option and it needs no admin consent by default.**
   Nothing narrower writes events. `Calendars.ReadBasic` and `Calendars.Read` only read,
   `Calendars.ReadWrite.Shared` is wider. The permissions reference marks the delegated
   `Calendars.ReadWrite` as `AdminConsentRequired: No` and "available for consent in personal
   Microsoft accounts". A tenant that disabled user consent blocks the user at the consent prompt
   and tells them to ask an admin; with the admin consent workflow on they can file a request from
   that prompt. A second, less obvious gate applies even where user consent is on: risk-based
   step-up consent, enabled by default, treats a newly registered multitenant app that is not
   publisher verified and asks for more than basic sign-in as risky and returns `AADSTS90094`.
4. **The existing registration takes the new permission; no second app.** The v2 endpoint consents
   incrementally: request `Calendars.ReadWrite offline_access` in a second authorize round from
   Settings and the prompt lists only the new permission. `offline_access` is what returns a refresh
   token and must be requested explicitly. Refresh tokens default to 90 days of inactivity, are
   replaced on every use, are not configurable, and survive a user's own password change for a
   confidential client; an admin reset from the Entra or M365 admin center or a user revoking all
   refresh tokens kills them. A refresh token is bound to user and client, not to a resource, so
   one token serves sign-in and Graph. Publisher verification is the one consequence: without it,
   point 3's step-up rule blocks consent in other companies' tenants.
5. **Call Graph with plain `fetch`.** `@microsoft/microsoft-graph-client` 3.0.7 was published
   2023-09-19 and is still `latest`; its README still asks Node users to bring a fetch polyfill and
   warns about Node 18's experimental fetch; its HTTP handler is a one-line call to the global
   `fetch`. The Kiota successor `@microsoft/msgraph-sdk` is at `1.0.0-preview.91`. Without MSAL the
   refresh is one `POST` to `/common/oauth2/v2.0/token` with `grant_type=refresh_token`, the client
   secret and the stored refresh token; store the refresh token the response returns. The backend
   already has `src/utils/oauthTokens.ts` to encrypt and decrypt provider tokens the way better-auth
   does.

## 1. Out of office events

The `event` resource has `showAs` as a string with "the possible values are: `free`, `tentative`,
`busy`, `oof`, `workingElsewhere`, `unknown`", and `isAllDay`: "Set to true if the event lasts all
day. If true, regardless of whether it's a single-day or multi-day event, start, and endtime must be
set to midnight and be in the same time zone." A timed event is the same resource with `start` and
`end` as `dateTimeTimeZone` values. `transactionId` is "a custom identifier specified by a client
app for the server to avoid redundant POST operations in case of client retries to create the same
event"; it cannot change after creation and is only returned if the app set it. `iCalUId` is "a
unique identifier for an event across calendars", read-only. The `id` changes when an item moves
between calendars unless the request carries `Prefer: IdType="ImmutableId"`.

`Create event` posts to `/me/events` (default calendar), `/me/calendar/events` or
`/me/calendars/{id}/events`, with the permissions table reading `Calendars.ReadWrite` on all three
rows: delegated work or school, delegated personal Microsoft account, application. `Update event`
(`PATCH`) and `Delete event` carry the same table, and `showAs`, `isAllDay`, `start`, `end`,
`subject`, `body`, `isReminderOn` and `sensitivity` are among the properties `PATCH` accepts.
Nothing on these pages distinguishes outlook.com mailboxes from Exchange Online ones, and the known
issues page has one calendar entry, about attaching large files to events in shared or delegated
mailboxes.

Two details for the implementation. `dateTimeTimeZone.timeZone` accepts Windows names such as
`Central Europe Standard Time` plus a listed set of IANA names; that list has `Europe/Berlin`,
`Europe/Budapest` and `Europe/Warsaw` but not `Europe/Prague`, so either send the Windows name or
test the IANA one before relying on it. `Prefer: outlook.timezone="..."` controls the time zone of
the response, not of the stored event.

## 2. Work location

The answer to "is there an API" is yes. `workHoursAndLocationsSetting` "represents a user's working
hours and location preferences for modern hybrid work scenarios" and lives at
`/me/settings/workHoursAndLocations` on v1.0; the resource, `workPlanRecurrence`,
`workPlanOccurrence` and their methods all carry `ms.date` 2025-12-19, and Graph's what's-new page
lists them as generally available in December 2025. The data model is a set of weekly
`workPlanRecurrence` objects (`workLocationType` of `unspecified`, `office` or `remote`, never
`timeOff`, with a `patternedRecurrence`) that generate `workPlanOccurrence` objects, plus manual
occurrences. `workLocationType` on an occurrence is `unspecified`, `office`, `remote` or `timeOff`;
`placeId` points into the Places directory and applies to `office` only.

The permissions table is identical on every method: delegated work or school `Calendars.ReadWrite`
(read methods accept `Calendars.Read`), delegated personal Microsoft account "Not supported",
application "Not supported" except through `/users/{id}`. So personal accounts are out regardless
of what the app does.

What a delegated caller can write:

| Call                                                                        | What it sets                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST .../occurrences/setCurrentLocation` `{workLocationType, updateScope}` | `office` or `remote` for `currentSegment` or `currentDay`. "This action quickly updates the user's work location without modifying individual occurrences." Returns 204.                                                                               |
| `POST .../occurrences`                                                      | "Only time-off occurrences can be created directly. The **workLocationType** must be set to `timeOff`. Other occurrences are autogenerated from recurrences." Takes `start`, `end` and `timeOffDetails {subject, isAllDay}`. Returns 201 with an `id`. |
| `PUT .../occurrences/{id}`                                                  | Full-object replace, "PATCH isn't supported". The only example is a `timeOff` occurrence; the page does not say whether an autogenerated `office` occurrence may be rewritten as `remote`.                                                             |
| `POST .../recurrences`, `PUT`, `DELETE`                                     | The user's weekly pattern. Rewriting it to express one Home office day would clobber what the user set in Outlook.                                                                                                                                     |
| `GET .../occurrencesView(startDateTime=,endDateTime=)`                      | Occurrences in a range, including autogenerated ones with their `id` and `recurrenceId`. Accepts `Calendars.Read`.                                                                                                                                     |

The beta pages for the same methods carry the same `timeOff`-only rule and the same "Not supported"
for personal accounts, so beta adds nothing here.

What this means for an approved Home office day some days ahead: there is no documented call that
writes `remote` onto a future date. The two honest options are a `setCurrentLocation` call with
`remote` and `currentDay` fired on the morning of that day in the user's time zone, which needs
day-of scheduling the sync does not otherwise have, or writing nothing for Home office on Microsoft.
A `PUT` of the autogenerated occurrence to `remote` is a third option the docs neither promise nor
forbid; if the spec wants it, a probe against a real Microsoft 365 mailbox decides, and the result
should be recorded next to this note.

Licensing: Microsoft Learn's Places overview, as indexed on 2026-10-11, puts work plans and
workplace presence in the core Places tier that Business Basic, Business Standard, Business Premium,
E1, E3, E5 and Teams licences include; the licensing page itself returned 404 on the day, so this
rests on the search index and should be confirmed before the spec depends on it. The API gate that
is documented is the account class: an Exchange Online mailbox in a Microsoft 365 tenant.

## 3. Scopes and consent

Permissions by operation on v1.0, delegated, least privileged first:

| Operation                            | Work or school                                                 | Personal Microsoft account |
| ------------------------------------ | -------------------------------------------------------------- | -------------------------- |
| List calendars `GET /me/calendars`   | `Calendars.ReadBasic`; also `ReadWrite`, `Read`, `Read.Shared` | same                       |
| Create calendar `POST /me/calendars` | `Calendars.ReadWrite`                                          | `Calendars.ReadWrite`      |
| Create, update, delete event         | `Calendars.ReadWrite`                                          | `Calendars.ReadWrite`      |
| Work hours and locations (any write) | `Calendars.ReadWrite`                                          | not supported              |

The permissions reference (`ms.date` 2026-09-14) describes the delegated `Calendars.ReadWrite`
(`1ec239c2-d7c9-4623-a91a-a9775856bb36`) as "Have full access to user calendars", "Allows the app to
create, read, update, and delete events in user calendars", `AdminConsentRequired: No`, and adds
that it "is available for consent in personal Microsoft accounts". The only other write-capable
delegated permission is `Calendars.ReadWrite.Shared`, which adds delegate and shared calendars and
is not available for personal accounts. There is nothing narrower than `Calendars.ReadWrite` that
writes; `Calendars.ReadBasic` and `Calendars.Read` only read. Since the write scope already lists
calendars, the app needs exactly `Calendars.ReadWrite` plus `offline_access`.

How a locked-down tenant looks to the user. Entra's default is that "all users are allowed to
consent to applications for permissions that don't require administrator consent", so a plain
tenant lets the user accept `Calendars.ReadWrite` themselves. Admins can switch to "Do not allow
user consent" or to "Allow user consent for apps from verified publishers, for selected
permissions", where the permission must also be classified low impact by that tenant. In either
case the consent prompt tells non-admin users they are "blocked from granting consent to the
application, and they're told to ask their admin for access to the app. If admin consent workflow is
enabled in the user's tenant, users are able to submit a request for admin approval from the consent
prompt." The workflow is off until a Global Administrator turns it on; when on, reviewers get an
email and the user is notified of the outcome.

Risk-based step-up consent is the gate most likely to bite. It "is enabled by default, but it
results in a behavior change only when user consent is enabled", and treats as risky "consent
requests for newly registered multitenant apps that aren't publisher verified and require nonbasic
permissions". When that fires and the admin consent workflow is off, the user sees
"**AADSTS90094**: <clientAppDisplayName> needs permission to access resources in your organization
that only an admin can grant." The publisher-verification overview puts the same rule as: since
November 2020 "users can't consent to most newly registered multitenant apps that _aren't_ publisher
verified" when they "request permissions that extend beyond the basic sign-in and read user profile"
in a tenant other than the registering one. Flexi Day's registration meets every part of that
description once it asks for `Calendars.ReadWrite`.

## 4. App registration, consent rounds and refresh tokens

One registration. Delegated permissions can be consented "Dynamic: request individual permissions
at sign-in", and the consent prompt appears "when the application uses dynamic consent to ask for
new permissions as needed at run time". The authorize request's `scope` "can cover multiple
resources", and omitting the resource prefix means Graph, so `scope=openid profile email
offline_access Calendars.ReadWrite` on a second authorize round from Settings is the whole change on
the request side. Adding `Calendars.ReadWrite` under API permissions on the registration is what
makes the `.default` and admin-consent paths list it, so do that too, but it is not what grants
anything. Keep the sign-in scopes as they are; the calendar round is a separate connect action.

`offline_access` "gives your app access to resources on behalf of the user for an extended time",
appears on the consent page as "Maintain access to data you have given it access to", and on the
v2 endpoint "your app must explicitly request the `offline_access` scope, to receive refresh
tokens". The token response's `refresh_token` is "Only provided if `offline_access` scope was
requested."

Lifetime and revocation. Refresh tokens default to "90 days for all other scenarios" (24 hours only
for SPAs and email one-time passcode). "Refresh tokens replace themselves with a fresh token upon
every use. The Microsoft identity platform doesn't revoke old refresh tokens when used to fetch new
access tokens. Securely delete the old refresh token after acquiring a new one." Configurable token
lifetimes retired refresh token settings on 2021-01-30; the only default left is
`MaxInactiveTime` 90 days, with max age "Until-revoked", and token lifetime policies "aren't
supported for applications developed for personal Microsoft accounts" anyway. For a confidential
client token, a password change by the user and a self-service reset leave the token alive; an admin
reset through the Entra admin center or M365 admin center, the user revoking their refresh tokens,
or an admin revoking all of them, revoke it. Access tokens last "a random value ranging between
60-90 minutes (75 minutes on average)". Refresh tokens "are bound to a combination of user and
client, but aren't tied to a resource or tenant", and "are valid for all permissions that your
client has already received consent for", so once the user has consented to `Calendars.ReadWrite`
the one stored refresh token mints Graph tokens.

Publisher verification. Section 3 explains why it matters: step-up consent blocks unverified
multitenant apps asking for more than sign-in in foreign tenants. The programme itself has no fee
and no licence, but the registration must have been created by a work or school account ("Apps that
are registered by using a Microsoft account can't be publisher verified"), the publisher domain
cannot be `*.onmicrosoft.com`, and the tenant must be tied to a verified Partner Center global
account. `todo/microsoft-entra-oauth.md` in the workspace already walks that chain; the calendar
feature turns it from cosmetic into a prerequisite for work tenants.

## 5. Client and token refresh without MSAL

State of `@microsoft/microsoft-graph-client` on 2026-10-11 (npm registry and GitHub):

- `latest` is 3.0.7, published 2023-09-19; 3.0.6 was 2023-08-24. The `dev` branch's `package.json`
  reads 3.0.8, unreleased; the last push was 2026-06-18; the repository is not archived and has 114
  open issues.
- `engines.node` is `>=12.0.0`. The README says "Node.js 12 LTS or higher", tells Node users "you
  will need to import any fetch polyfill which suits your requirements" (isomorphic-fetch,
  cross-fetch, whatwg-fetch), and for Node 18 recommends "disable the experimental `fetch` feature"
  with `--no-experimental-fetch`. `src/middleware/HTTPMessageHandler.ts` does
  `context.response = await fetch(context.request, context.options)` with no import, so on Node 24
  it uses the native `fetch` and the polyfill advice is stale rather than wrong.
- Learn's "choose an authentication provider" page assumes `@azure/identity` credentials wrapped in
  `TokenCredentialAuthenticationProvider`; the repository's own doc allows any class implementing
  `AuthenticationProvider` with a single `getAccessToken(): Promise<string>`, or `Client.init` with a
  `(callback) => callback(error, accessToken)` provider. The default middleware is
  AuthenticationHandler, RetryHandler, RedirectHandler, TelemetryHandler, HTTPMessageHandler.
- The next-generation package `@microsoft/msgraph-sdk` (Kiota) is `1.0.0-preview.91`, published
  2026-10-06, still preview.

Recommendation: plain `fetch` against `https://graph.microsoft.com/v1.0`. The sync touches a
handful of endpoints (`/me/calendars`, `/me/events`, `/me/calendars/{id}/events/{id}`, optionally
`/me/settings/workHoursAndLocations/occurrences/setCurrentLocation`), and the SDK's value, a fluent
URL builder, batching and a retry handler, does not outweigh a dependency last released three years
ago with a `tslib`/`@babel/runtime` runtime footprint. `@microsoft/microsoft-graph-types` (2.43.1,
2026-07-16) can still supply the TypeScript shapes for `Event` and `Calendar` without pulling the
client. Handle `429` and `503` with `Retry-After` yourself; Graph's throttling guidance was not part
of this research.

Refresh without MSAL is one request, documented in the auth code flow reference:

```http
POST https://login.microsoftonline.com/common/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

client_id={MICROSOFT_CLIENT_ID}
&client_secret={MICROSOFT_CLIENT_SECRET}
&grant_type=refresh_token
&refresh_token={stored}
&scope=https%3A%2F%2Fgraph.microsoft.com%2FCalendars.ReadWrite%20offline_access
```

`client_secret` is "required for web apps"; `scope` is optional and "must be equivalent to or a
subset of the scopes requested in the original `authorization_code` request leg". The response
carries `access_token`, `expires_in` and a new `refresh_token`; "Replace the old refresh token with
this newly acquired refresh token to ensure your refresh tokens remain valid for as long as
possible." Errors come back as `invalid_grant` (expired or revoked: send the user back through the
connect flow), `interaction_required` and `consent_required`. Do not decode the Graph access token:
"Tokens for Microsoft services can use a special format that will not validate as a JWT, and may
also be encrypted for consumer (Microsoft account) users."

The backend already has the storage half. `src/utils/oauthTokens.ts` exposes `encryptOAuthToken` and
`decryptStoredOAuthToken`, wrapping better-auth's `setTokenUtil` and `decryptOAuthToken`, so the
calendar connection's refresh token can sit in the same encrypted form as the sign-in tokens.
`todo/microsoft-entra-oauth.md` records the current registration: Web platform, redirect
`{BETTER_AUTH_URL}/api/auth/callback/microsoft`, scopes `openid profile email User.Read
offline_access`, tenant `common`.

- If the spec wants a future-dated Home office, probe `PUT .../occurrences/{id}` with
  `workLocationType: remote` on an autogenerated occurrence against a real Microsoft 365 mailbox and
  record the outcome here.
- Confirm the Places licensing tier for work plans against the Learn page once it resolves.
- Treat publisher verification as a launch prerequisite for the Microsoft calendar connector, not a
  cosmetic follow-up.
- Pick the time zone representation for all-day events (`Central Europe Standard Time` or UTC
  midnight) and verify `Europe/Prague` against the API before using IANA names.
